# MK audit findings — 2026-05-06

Análise da saída do `audit.rsc` rodado no MikroTik **hEX RB750Gr3** (RouterOS
6.49.10, uptime 1d19h, IP público 177.223.44.35 via PPPoE `pppoe-out1`).

## Resumo executivo

Existem **18 port-forwards (`dstnat`)** expostos no IP público sem nenhuma
restrição de origem. Vários publicam serviços críticos (Redis, SQL Server,
PostgreSQL, RabbitMQ, RDP×3) diretamente na internet. Não há firewall de
**input/forward** filtrando origem para esses serviços. Não há queues. O
NetFlow captura `interfaces=all`, dobrando o volume de flows armazenados.

A hipótese inicial de "DVR/CFTV" para os hosts `.54/.122/.220/.41` está
**errada**: pelos DHCP leases, são PCs/servers Windows (HP/Lenovo). O destino
dos uploads (45.65.220.x e variantes brasileiras) coincide com o **DNS
dinâmico do próprio ISP** (45.65.220.23) — provavelmente algum software
corporativo (sistema fiscal, ponto eletrônico, sync) hospedado lá. Identificar
qual processo está fazendo o upload nesses 4 hosts é o próximo passo.

## Achados, em ordem de criticidade

### 🔴 CRÍTICO — port-forwards perigosos sem ACL

| Porta WAN | → LAN | Serviço | Por que é grave |
|---|---|---|---|
| 6379  | 192.168.2.116 | **Redis** | RCE via `CONFIG SET dir/dbfilename + SAVE` (técnica conhecida); só seguro se `requirepass` forte e binds restritos |
| 5672  | 192.168.2.116 | RabbitMQ AMQP | Default user `guest/guest`, brute-force trivial |
| 15672 | 192.168.2.116 | RabbitMQ Mgmt UI | Painel web público |
| 11433 | 192.168.1.109 | **SQL Server** | TDS protocol exposto, brute-force, RCEs históricos (xp_cmdshell etc) |
| 55565 | 192.168.2.103 | PostgreSQL | mesmo de cima para PG |
| 6557  | 192.168.1.109 | PostgreSQL | mesmo de cima |
| 21232 | 192.168.1.109:3390 | RDP Win | BlueKeep, NLA, força bruta |
| 21233 | 192.168.1.67:3389  | RDP Win | mesmo |
| 21234 | 192.168.1.122:3389 | RDP Win | mesmo |
| 22242, 22243, 22245-7 | vários | SSH | aceitável se key-only e fail2ban; ainda assim alvo constante |

**Mitigação**: adicionar `src-address-list=allowed-mgmt` em cada `dstnat` e/ou
filtros `chain=forward action=drop` antes do match das DST-NAT. Ver
`mitigations-v2.rsc`.

### 🟠 ALTO — sem firewall input default

`/ip firewall filter` não tem `chain=input action=drop in-interface-list=WAN`.
Significa: input default-accept para a WAN. Apenas Winbox (8291) está aberto
no `/ip service`, mas o NAT joga tráfego direto para os destinos LAN sem
passar por filtro.

### 🟠 ALTO — DSTNAT 80/443 → 192.168.2.32 expõe TODOS os domínios do nginx

A regra `dst-nat to-addresses=192.168.2.32 port=80,443` é catch-all. Já há
geo-block para `prometheus.sittax.com.br` no nginx (geo $allowed_ip). Mas o
nginx hoje **respondeu 404** para um exploit IoT chegando direto pelo IP
público (`/device.rsp?...wget...arm7`). Conferir se há algum upstream
publicando endpoints sensíveis sem autenticação.

### 🟡 MÉDIO — RouterOS 6.x com 4.6 MB livres no flash

`6.49.10` é long-term válido, mas a série 7.x é mais nova e tem features de
firewall melhores (e.g. `address-list` automático por `tarpit`). Mais urgente:
**4.6 MiB livres em 16 MiB** de flash — risco de não conseguir gravar logs ou
cache de DNS. Limpar arquivos antigos (`/file print`).

### 🟡 MÉDIO — bridge1 com .1.0/24 e .2.0/24 simultâneos

```
bridge1 = ether2 + ether3 + ether4 + ether5
ip address: 192.168.1.1/24, 192.168.2.1/24 (ambos na mesma bridge)
```

É **um único broadcast domain**, não duas redes. Os flows que mostravam
`192.168.1.109 → 192.168.1.1:porta-alta` eram tráfego do dev-server pro
gateway via L2 (resposta a clientes da .2.x). Bom de saber: **não há
roteamento entre subnets no MK** porque elas estão na mesma bridge L2. Para
isolar (recomendado), seria preciso bridge filter, vlans, ou L3 forçado.

### 🟡 MÉDIO — Sem queue / sem QoS

`/queue tree` e `/queue simple` vazios. Saturação de upload por qualquer host
afoga o resto da rede. Sugestão em `mitigations-v2.rsc`: queue PCQ por host
com fairness, e queue separada limitando upload pesado.

### 🟢 BAIXO — NetFlow captura `interfaces=all`

`/ip traffic-flow interfaces=all` exporta flows duas vezes para tráfego
LAN→WAN (uma na ether/bridge LAN e outra no `pppoe-out1`). Trocar para
`interfaces=pppoe-out1` corta volume pela metade e ainda mantém todo o
tráfego internet visível. Para visibilidade intra-LAN, manter um target
secundário ou usar o mirror TZSP que já está configurado.

### 🟢 BAIXO — TZSP streaming desligado

`/tool sniffer` tem `streaming-server=192.168.2.50:37008` configurado, mas
`running=no`. O container `netmon-tshark` está esperando pacotes que não
chegam. Para ativar quando precisar: `/tool sniffer start`.

## Address-list "bloqueados"

Já contém:
* 192.168.1.39 (manual antigo)
* 192.168.1.54 (adicionado hoje 10:41 — provavelmente após o pico)

A regra `chain=forward action=drop src-address-list=bloqueados` (e a versão
`dst-address-list`) cobre apenas tráfego que **atravessa** a bridge. Como
.54 está fazendo upload pra WAN, o pacote do `.54 → externo:8080` passa por
`forward` e é dropado ✓.

**Atenção**: se você só queria limitar e não bloquear total, troque para a
queue de `mitigations-v2.rsc`.
